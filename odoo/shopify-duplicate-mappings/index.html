Shopify orders linked to archived / wrong products – duplicate mappings (26.10.2026)

Status 26.10.2026, 14:30: in progress. Cause found, method proven on 2 of 27 wrong mappings, 3 orders to correct. Follow-up of the Shopify instance archive incident (23.10.2026).

Odoo 19 Production · Emipro Shopify connector · instance IQ Dogsport Shopify (id 1). All investigation was done with read-only commands. Customer data is not stored here.

1. Symptom

Order #IQD-99075 contained the archived product [IQD-EGE-WUV-0010] Wurfversteck (id 312, stock 0 → delivery "Nicht verfügbar"), although the active product IQ Wurfversteck / IQ Pop-Up Blind (id 676, same SKU, 28 in stock) exists and had been sold 421 times.

2. How the connector finds the product

The connector does not search by product name. It uses its mapping table shopify.product.product.ept ("Shopify layer variant"): Shopify variant ID → Odoo product. If a Shopify variant has several active mappings, it can take the wrong one (here the older record).

3. Root cause

  • When products were replaced (new version, merge), a new mapping was created for the same Shopify variant; the old mapping was archived. Old and new product often keep the same SKU.
  • On 23.10.2026 13:29:21 UTC the instance was archived by mistake and reactivated. The reactivation set all layer records active again, including the old, intentionally archived mappings (write_date of both Wurfversteck mappings = exactly 13:29:21).
  • Since then those Shopify variants have two or three active mappings → new orders could land on archived or wrong products. Before 23.10 no order used product 312.
  • Special case PSD: the PSD Shopify variants still had an old mapping to the TDP.OL products (variant probably reused in Shopify) → a PSD order arrived as a different article.

5. Fix procedure (one mapping)

  1. Before (read-only): list all mappings of the Shopify variant (query 8.1) – expect one wrong + one correct, both active.
  2. Open https://iq-dogsport.odoo.com/odoo/shopify.product.product.ept/<ID>. Check instance, Shopify variant, Default Code and that Product is the old/wrong one.
  3. ⚙ → Archive. Never archive the correct mapping, never archive the Shopify layer product (template).
  4. After: run query 8.1 again → wrong = f, correct = t. Check the product is unchanged in Shopify.
  5. Re-check after ~1 hour that it stays archived (done for 749: still archived ✓).

Careful: Inventory → Product Variants lists Odoo products with different IDs (there id 749 is "Chest and back patch with print"). The mappings are only in model shopify.product.product.ept.

Why it is safe: archiving a mapping only hides it from the connector; nothing is sent to Shopify (proven on 23.10, when all mappings were archived and the shop kept working) and it is reversible (filter Archived → Unarchive). Existing orders are not changed by it.

Remaining 25 at once (after the proven single tests)

Open https://iq-dogsport.odoo.com/odoo/shopify.product.product.ept → Add Custom Filter (code editor):

7. Prevention

  • Never archive / deactivate the Shopify instance (Production or Staging). Staging: use Reset Credentials or a separate instance.
  • When replacing a product: map the Shopify variant to the new product, archive the old mapping at the same time, and give the archived Odoo product a unique SKU (e.g. …-ALT) so it can never be matched again. (SKU change on existing archived products: to be agreed before doing it.)
  • Weekly check with queries 8.3 and 8.4 (read-only). Optional later: scheduled action that creates an activity when they find something (needs go-ahead).
  • About 250 more active mappings point to archived products without a duplicate. They only matter if that Shopify variant is still for sale – review later.

8. Read-only queries (Odoo.sh → Production → SHELL)

8.1 All mappings of one Shopify variant

PGOPTIONS='-c default_transaction_read_only=on' psql -P pager=off -c "SELECT s.id, to_jsonb(s)->>'variant_id' AS shopify_variant, s.product_id, pp.default_code, pp.active AS product_active, s.active AS mapping_active, s.write_date FROM shopify_product_product_ept s JOIN product_product pp ON pp.id = s.product_id WHERE to_jsonb(s)->>'variant_id' = '53151323881736' ORDER BY s.id;"

8.2 Wrong mappings (archived product while a correct active mapping exists)

PGOPTIONS='-c default_transaction_read_only=on' psql -P pager=off -c "SELECT bad.id AS wrong_layer, to_jsonb(bad)->>'variant_id' AS shopify_variant, bad.product_id AS wrong_product, pb.default_code AS wrong_sku, good.id AS right_layer, good.product_id AS right_product, pg.default_code AS right_sku FROM shopify_product_product_ept bad JOIN product_product pb ON pb.id = bad.product_id JOIN shopify_product_product_ept good ON to_jsonb(good)->>'variant_id' = to_jsonb(bad)->>'variant_id' AND good.id <> bad.id AND good.active AND good.shopify_instance_id = 1 JOIN product_product pg ON pg.id = good.product_id AND pg.active WHERE bad.active AND NOT pb.active AND bad.shopify_instance_id = 1 ORDER BY bad.id;"

8.3 Variants mapped to more than one different product

PGOPTIONS='-c default_transaction_read_only=on' psql -P pager=off -c "SELECT to_jsonb(s)->>'variant_id' AS shopify_variant, string_agg(s.id::text || '->' || s.product_id::text, ', ') AS layer_to_product FROM shopify_product_product_ept s WHERE s.active AND s.shopify_instance_id = 1 GROUP BY 1 HAVING count(DISTINCT s.product_id) > 1;"

8.4 Orders of the last 7 days with archived products

PGOPTIONS='-c default_transaction_read_only=on' psql -P pager=off -c "SELECT so.name, so.create_date, pp.default_code FROM sale_order_line sol JOIN sale_order so ON so.id = sol.order_id JOIN product_product pp ON pp.id = sol.product_id WHERE so.create_date > now() - interval '7 days' AND NOT pp.active;"
