2. Combined automation — automatic DHL shipping method

Original problem: the first two Sales Order rules assigned fixed delivery methods by country. Two rules worked but were more complicated to maintain. They were consolidated into one On create Execute Code action in Staging.

SettingValue
ModelSales Order (sale.order)
TriggerOn create
Apply onDelivery Method is not set; Delivery Address Country is set
Action typeExecute Code (one combined conditional action)
GermanyDE → DHL Parcel DE / V01PAK
Staging internationalCountry not DE → DHL Parcel DE – International / V53WPAK
Safety ruleDo not overwrite a Delivery Method already selected on the Sales Order

Reference Python code (must verify against saved action)

# Reference example - NOT verified against final saved Odoo action
# Model: sale.order | Trigger: On create
orders = records or record or env['sale.order']
for order in orders:
    if order.carrier_id:
        continue  # Preserve a previously selected shipping method
    country = order.partner_shipping_id.country_id
    if not country:
        continue
    carrier_name = (
        'DHL Parcel DE' if country.code == 'DE'
        else 'DHL Parcel DE – International'
    )
    carriers = env['delivery.carrier'].search([
        ('name', '=', carrier_name),
        ('delivery_type', '=', 'dhl_parcel_de'),
    ])
    if len(carriers) != 1:
        log('DHL carrier not unique: %s' % carrier_name, level='warning')
        continue
    order.write({'carrier_id': carriers.id})
Production limitation: A blank carrier on a new Shopify order does not necessarily mean the customer selected DHL. This defaulting logic must be reconciled with the Shopify-to-Odoo shipping mapping, GLS choices and supported countries before going live. Do not automatically offer DHL to every country merely because its code is not DE.

3. Automation 66 — copy the selected DHL carrier to the outgoing delivery

Original failure: Sales Order S00462 for Austria contained DHL International, but WH1/OUT/06242 displayed GLS Germany. Investigation confirmed no general default carrier, Propagate Carrier = True on the stock rule, and correctly linked stock moves.

Automation 66 repairs the mismatch on outgoing deliveries. It must select the exact DHL carrier record from the sales order and avoid changing completed shipments or shipments already carrying a tracking number.

Reference Python code (not verified final saved code)

# Reference example - NOT verified against final saved Odoo action
# Model: stock.picking | Trigger: On create and edit
pickings = records or record or env['stock.picking']
for picking in pickings:
    if picking.picking_type_id.code != 'outgoing':
        continue
    if picking.state in ('done', 'cancel'):
        continue
    if picking.carrier_tracking_ref:
        continue
    so = picking.sale_id
    if not so or not so.carrier_id:
        continue
    if so.carrier_id.delivery_type != 'dhl_parcel_de':
        continue  # Do not turn GLS orders into DHL orders
    if picking.carrier_id.id != so.carrier_id.id:
        picking.write({'carrier_id': so.carrier_id.id})
        log('Carrier synchronized: %s -> %s' %
            (picking.name, so.carrier_id.name), level='info')

Do not add a second conflicting transfer rule. If a warehouse operator intentionally changes a carrier, the automation's behavior around that manual override should be tested before Production.

4. Automation 64 — automatic German Return Receiver ID

Original issue: the DHL Return Receiver ID was empty on new returns. Warehouse staff had to open Get Receivers and manually select an entry for each German return.

SettingConfigured value
ModelTransfer (stock.picking)
TriggerOn create and edit
Before Update DomainMatch all records
Apply on[('dhl_return_receiver_id', '=', False)]
When updatingCarrier, Contact, Operation Type — do not monitor Receiver ID itself
ActionExecute Code
ResultIncoming DHL return from Germany → deu if receiver is blank

Documented Python implementation

# Documented German DHL return-receiver logic
# Model: stock.picking | Execute Code
pickings = records or record or env['stock.picking']
for picking in pickings:
    if not picking.is_dhl_return:
        continue
    if picking.picking_type_id.code != 'incoming':
        continue
    if picking.carrier_id.delivery_type != 'dhl_parcel_de':
        continue
    if picking.state in ('done', 'cancel'):
        continue
    if picking.dhl_return_receiver_id:
        continue  # Preserve manual receiver selection
    if picking.partner_id.country_id.code == 'DE':
        picking.write({'dhl_return_receiver_id': 'deu'})
        log('DHL receiver deu assigned to %s' %
            picking.name, level='info')

is_dhl_return is a non-stored computed field, so the automation checks it in Python rather than placing it inside an Odoo search domain. The existing-receiver guard is essential: a manually chosen receiver is not overwritten.

9. Production rollout — do not deploy Staging blindly

  1. Export and archive the exact saved Python of the combined automation and automation 66; identify the new combined automation's ID.
  2. Back up Production and check BrowseInfo DHL connector compatibility and delivery-method configurations.
  3. Review actual Shopify shipping preferences and Emipro carrier mapping. Customer-selected GLS must not silently turn into DHL.
  4. Restrict DHL availability to supported destinations; verify international billing number and product V53WPAK; domestic remains V01PAK.
  5. Verify DHL production credentials/API entitlements and legitimate customer charge arrangements before any live label use.
  6. Create or migrate the three verified automations and one inherited button view in Production; note that Odoo IDs may differ between environments.
  7. Keep obsolete fixed-carrier automations inactive and check existing Production automations for conflicts.
  8. Test a DE sale, an international sale, and an explicit GLS sale from order to outgoing picking, without generating labels until carrier values are correct.
  9. Test a German return (auto receiver deu) and the manual Change Receiver workflow before validating incoming goods.
  10. Only after approval, test a controlled real DHL label, check receiver and address, tracking, label printing and billing.
Reminder: Odoo Staging changes do not automatically appear in Production. GitHub Dogsport/odoo-customizations is a documentation repository, not an Odoo deployment pipeline.

10. Export the exact saved code (read-only Shell)

To make the technical record complete, run this in Odoo Staging Shell and replace the two reference examples in this HTML with the code actually saved in your actions.

# READ ONLY: export the actual saved automation source in Staging.
for aid in [64, 66]:
    a = env['base.automation'].sudo().browse(aid)
    print('Automation:', a.id, a.name, 'active:', a.active,
          'trigger:', a.trigger)
    for action in a.action_server_ids:
        print('Action:', action.name, '| type:', action.state)
        if action.state == 'code':
            print(action.code)

# Identify the combined automation (ID is not yet documented).
for a in env['base.automation'].sudo().search([
    ('model_id.model', '=', 'sale.order'),
    ('active', '=', True),
]):
    print('Sale automation:', a.id, a.name, a.trigger)

This command prints automation code only to the Shell output and does not change database records. Avoid copying API keys, passwords, client secrets or tokens into the GitHub article.
